## 1. Declaración del Requerimiento

En el marco de la gobernanza técnica y modelado pre-código de **DevSculptor**, el lienzo de modelado entidad-relación (ERD) debe proveer una **capa agnóstica de traducción de esquemas DDL** (*Data Definition Language*). 

La generación de scripts DDL no debe estar acoplada únicamente a PostgreSQL, sino que debe permitir exportar e inspeccionar de forma determinista la estructura relacional para los cuatro principales motores de bases de datos relacionales de la industria:

1. **PostgreSQL** (dialecto nativo del proyecto y estándar de producción)
2. **MySQL / MariaDB**
3. **SQLite** (entornos móviles, edge y prototipado local)
4. **Oracle Database** (entornos corporativos enterprise)

---

## 2. Principio de Arquitectura: Capa de Traducción Pura

La representación interna de una entidad en DevSculptor (`CanvasEntity` con `columns_json`) actúa como un **Modelo de Objeto Canónico de Esquema** (*Canonical Schema Object Model*). 

Cualquier generador de script DDL es una **función pura sin efectos secundarios** que traduce la definición canónica a la sintaxis idiomática de cada dialecto SQL:

```
[ Canvas Canonical Schema (JSONB) ]
                 │
  ┌──────────────┼──────────────┬──────────────┐
  ▼              ▼              ▼              ▼
PostgreSQL     MySQL         SQLite         Oracle
  Dialect       Dialect       Dialect        Dialect
```

## 3. Matriz de Equivalencias de Tipos y Convenciones

| Tipo Canónico DevSculptor | PostgreSQL | MySQL / MariaDB | SQLite | Oracle Database |
| :--- | :--- | :--- | :--- | :--- |
| `UUID` (PK) | `UUID PRIMARY KEY DEFAULT gen_random_uuid()` | `CHAR(36) PRIMARY KEY` | `TEXT PRIMARY KEY` | `VARCHAR2(36) PRIMARY KEY` |
| `SERIAL` / `INT` (PK) | `SERIAL PRIMARY KEY` | `INT AUTO_INCREMENT PRIMARY KEY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `VARCHAR(n)` | `VARCHAR(n)` | `VARCHAR(n)` | `TEXT` | `VARCHAR2(n)` |
| `TEXT` | `TEXT` | `LONGTEXT` | `TEXT` | `CLOB` |
| `BOOLEAN` | `BOOLEAN DEFAULT true/false` | `TINYINT(1) DEFAULT 1/0` | `INTEGER DEFAULT 1/0` | `NUMBER(1) CHECK (col IN (0, 1))` |
| `TIMESTAMP` | `TIMESTAMPTZ DEFAULT NOW()` | `DATETIME DEFAULT CURRENT_TIMESTAMP` | `TEXT DEFAULT (datetime('now'))` | `TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP` |
| `JSONB` | `JSONB` | `JSON` | `TEXT` | `BLOB / JSON` |
| `DECIMAL(p, s)` | `DECIMAL(p, s)` | `DECIMAL(p, s)` | `REAL` | `NUMBER(p, s)` |

## 4. Gestión de Claves Foráneas y Cardinalidades

Cada motor procesa las restricciones de integridad referencial (`FOREIGN KEY`) según su estándar:
- **PostgreSQL / MySQL:** `CONSTRAINT fk_... FOREIGN KEY (origen) REFERENCES destino(id) ON DELETE CASCADE/SET NULL`.
- **SQLite:** `FOREIGN KEY (origen) REFERENCES destino(id)` dentro del cuerpo de la tabla, con `PRAGMA foreign_keys = ON;` al inicio del script.
- **Oracle:** Sentencias `ALTER TABLE origen ADD CONSTRAINT fk_... FOREIGN KEY (origen) REFERENCES destino(id);` separadas.

### Expresión de Cardinalidades:
- **1:1 (Uno a Uno):** Clave foránea con restricción `UNIQUE` en la columna origen.
- **1:N (Uno a Muchos):** Clave foránea estándar sin unicidad en el lado *Muchos*.
- **N:M (Muchos a Muchos):** Creación y sugerencia de tabla intermedia (*junction table*) con clave primaria compuesta y doble FK.
